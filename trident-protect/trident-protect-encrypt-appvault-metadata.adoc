= Trident Protect 스냅샷 및 백업용 AppVault 메타데이터 암호화
:hardbreaks:
:allow-uri-read: 
:nofooter: 
:icons: font
:linkattrs: 
:imagesdir: ../media/


[role="lead"]
Kubernetes Secrets의 민감한 정보를 포함하여 Trident Protect가 AppVault에 저장하는 스냅샷 및 백업 메타데이터를 암호화할 수 있습니다. 암호화된 데이터를 보호하는 암호도 변경할 수 있습니다. 암호를 한 번만 변경하면 메타데이터 암호화 키가 재암호화되고 AppVault의 모든 Kopia 리포지토리와 모든 Restic 리포지토리가 새 암호로 이동됩니다.

암호화는 기본적으로 비활성화되어 있습니다. 암호화를 활성화하면 Trident Protect는 메타데이터를 AppVault에 저장하기 전에 새 스냅샷 및 백업 메타데이터를 암호화합니다. 이렇게 하면 애플리케이션 스냅샷 또는 백업에서 해당 리소스를 명시적으로 제외하지 않는 한, Secrets의 민감한 정보를 포함한 애플리케이션 리소스를 보호할 수 있습니다.

금고 암호는 데이터를 암호화하는 키를 보호합니다. 다음 동작에 유의하십시오.

* 금고 암호를 변경하면 Trident Protect는 새 암호로 동일한 키를 보호합니다. 이미 암호화된 데이터는 다시 기록하지 않습니다.
* 암호화를 활성화하기 전에 저장된 데이터는 계속 읽을 수 있습니다.
* 암호화된 데이터는 나중에 새 데이터에 대한 암호화를 해제하더라도 읽을 수 있는 상태로 유지됩니다.


.이 작업에 대해
암호화를 활성화할 때, 사용자 지정 암호를 지정하지 않는 한 Trident Protect는 안전하지 않은 기본 암호를 사용합니다. 각 AppVault에 대해 사용자 지정 볼트 암호를 생성하고  `spec.vaultPasswordSecretRef`에서 이를 참조하십시오.

기본 암호로 암호화를 활성화한 후 나중에 사용자 지정 암호를 추가한 경우, 기존 데이터와 리포지토리가 사용자 지정 암호로 이동하도록 암호를 교체해야 합니다. <<볼트 비밀번호를 변경하십시오>>을(를) 참조하십시오.

각 AppVault에 대해 고유한 사용자 지정 암호를 사용하십시오. 한 번에 하나의 AppVault에 대해서만 암호를 교체하고, 다른 암호 변경을 시작하기 전에 교체가 완료되었는지 확인하십시오.

.시작하기 전에
다음 사항을 확인하십시오.

*  `trident-protect` 네임스페이스에 대한 액세스.
* Kubernetes Secret을 생성하고 AppVault 사용자 정의 리소스(CR)에 패치를 적용할 수 있는 권한입니다.
* 각 AppVault에 대해 계획된 별도의 암호 Secret입니다.




[[enable-metadata-encryption]]
== 메타데이터 암호화 활성화

Trident Protect에 대한 Helm 값을 설정하여 메타데이터 암호화를 활성화합니다.

.단계
.  `resourceBackupEncryptionEnabled`를 `true`로 설정하려면 `values.yaml` 파일을 사용하십시오:
+
.. 다음 내용을  `values.yaml` 파일에 추가하십시오:
+
[source, yaml]
----
resourceBackupEncryptionEnabled: true
----
.. 파일을 적용하십시오:
+
[source, console]
----
helm upgrade trident-protect -n trident-protect netapp-trident-protect/trident-protect -f values.yaml --reuse-values
----


. 또는 Helm `--set` 플래그를 사용하여 `resourceBackupEncryptionEnabled`을 `true`로 설정합니다.
+
[source, console]
----
helm upgrade trident-protect -n trident-protect netapp-trident-protect/trident-protect \
  --set resourceBackupEncryptionEnabled=true \
  --reuse-values
----


.결과
Trident Protect는 새 스냅샷 및 백업 메타데이터를 암호화합니다.

.다음 단계
각 AppVault에 대한 사용자 지정 볼트 암호를 생성하십시오. 생성하기 전까지 Trident Protect는 안전하지 않은 기본 암호를 사용합니다.



[[create-a-custom-vault-password]]
== 사용자 지정 볼트 암호 생성

사용자 지정 암호를 사용하려면 암호가 포함된 Kubernetes Secret을 생성한 다음 AppVault에서 Secret을 참조하십시오.

.이 작업에 대해
AppVault를 생성할 때 사용자 지정 암호를 구성하면, 데이터가 저장되기 전에 AppVault가 즉시 사용자 지정 암호를 사용합니다. 암호를 변경할 필요가 없습니다.

AppVault에 이미 Kopia 또는 Restic 저장소가 있는 경우 새 암호를 추가해도 해당 저장소의 암호는 변경되지 않습니다. 이 섹션의 단계를 사용하지 마십시오. 대신 <<볼트 비밀번호를 변경하십시오>>의 단계를 따르십시오.

해당  `VAULT_PASSWORD` 값은 다음 요구 사항을 충족해야 합니다:

* 비어있으면 안 됩니다
* 크기는 64 KiB보다 작아야 합니다
* NUL 문자를 포함해서는 안 됩니다.
* 줄 바꿈을 포함해서는 안 됩니다
* 공백이나 기타 공백 문자로 시작하거나 끝나서는 안 됩니다


비밀번호에는 비 ASCII 문자를 포함한 다른 문자가 포함될 수 있습니다.

.단계
. AppVault와 동일한 네임스페이스에 Secret을 생성합니다. Secret에는  `VAULT_PASSWORD`라는 이름의 키가 포함되어야 합니다:
+
[source, console]
----
kubectl -n trident-protect create secret generic vault-password \
  --from-literal=VAULT_PASSWORD='<password>'
----
+

NOTE: AppVault에서 암호가 유효하지 않다고 보고하는 경우,  `VAULT_PASSWORD` 값이 위의 요구 사항을 충족하는지 확인하십시오. 일반적인 원인으로는 암호 값이 비어 있거나, 끝에 줄 바꿈 문자가 있거나, 암호의 시작이나 끝에 공백이 있는 경우 등이 있습니다.

. AppVault CR의  `spec.vaultPasswordSecretRef` 필드에서 Secret을 참조하십시오:
+
[source, yaml]
----
apiVersion: protect.trident.netapp.io/v1
kind: AppVault
metadata:
  name: my-vault
  namespace: trident-protect
spec:
  vaultPasswordSecretRef: vault-password
  providerType: <provider-type>
  providerConfig:
    <provider-configuration>
----
+
 `spec.vaultPasswordSecretRef`이(가) 비어 있으면 AppVault는 안전하지 않은 기본 암호를 사용합니다.



.결과
AppVault는 사용자 지정 암호를 사용하여 메타데이터 암호화 키를 보호합니다.



[[rotate-the-vault-password]]
== 볼트 비밀번호를 변경하십시오

이미 데이터가 저장된 AppVault의 암호를 변경할 수 있습니다. 한 번 변경하면 메타데이터 암호화 키가 재암호화되고 AppVault의 모든 Kopia 리포지토리 및 모든 Restic 리포지토리가 새 암호로 이동됩니다.

.이 작업에 대해
순환하는 동안 Trident Protect는 다음과 같은 작업을 수행합니다:

* AppVault에 대해 실행 중인 백업 및 복원 작업이 완료될 때까지 기다린 후 시작합니다.
* 새 비밀번호로 메타데이터 암호화 키(`metadata-key.json`)를 보호합니다. 아카이브 오브젝트는 다시 쓰지 않습니다.
* AppVault 접두사 아래에 있는 각 Kopia 저장소와 각 Restic 저장소를 찾아 비밀번호를 새 비밀번호로 변경합니다. 이미 새 비밀번호로 열리는 저장소는 변경되지 않습니다.
* 백업 또는 복원 작업에서 여전히 사용 중인 저장소는 건너뛰고 나중에 다시 시도합니다.
* AppVault를 참조하는 활성화된 일정을 일시 중지합니다. 각 일정에 대해 Trident Protect는  `spec.enabled`을(를)  `false`(으)로 설정하고 다음 주석을 추가합니다:
+
[source, yaml]
----
protect.trident.netapp.io/vault-password-rotation-suspended: <namespace>/<appvault-name>
----


순환이 완료되면 Trident Protect는 이 주석이 있는 일정만 다시 활성화합니다. 순환에 실패하면 중단된 지점부터 다시 시작합니다. 이미 새 암호를 사용하는 저장소는 다시 변경되지 않습니다.

.시작하기 전에
다음 사항을 확인하십시오.

* <<사용자 지정 볼트 암호 생성,볼트 비밀번호 요구 사항>>을(를) 충족하는 새 비밀번호.
* 다른 AppVault는 암호를 변경하고 있지 않습니다. 여러 AppVaults가 동일한 버킷과 접두사를 공유하는 경우, 그중 하나만 암호를 변경할 수 있습니다. <<버킷을 공유하는 AppVaults의 로테이션을 관리합니다>>을(를) 참조하십시오.


.단계
. 현재 Secret과 다른 이름으로 새 Secret을 생성하십시오:
+
[source, console]
----
kubectl -n trident-protect create secret generic vault-password-new \
  --from-literal=VAULT_PASSWORD='<new-password>'
----
+

IMPORTANT: 순환이 완료되기 전에 현재 시크릿을 수정하거나 삭제하지 마십시오. Trident Protect는 모든 저장소가 새 암호를 사용할 때까지 기존 데이터를 열기 위해 현재 암호가 필요합니다. 현재 시크릿을 너무 일찍 삭제한 경우, 동일한 이름과 원래 `VAULT_PASSWORD` 값으로 다시 생성하십시오.

. 회전을 활성화하고 AppVault가 새 Secret을 사용하도록 설정합니다.  `my-vault`을(를) AppVault 이름으로 바꿉니다:
+
[source, console]
----
kubectl -n trident-protect patch appvault my-vault --type merge --patch '
spec:
  enableRotation: true
  vaultPasswordSecretRef: vault-password-new
'
----
+

NOTE: 비밀번호를 변경하기 전에  `spec.enableRotation`을(를)  `true`(으)로 설정해야 합니다. 이 값이  `false`인 경우, AppVault는 순환이 비활성화되었다고 보고하고 비밀번호를 변경하지 않습니다.

. <<비밀번호 변경 모니터링>>의 단계를 따라 회전을 모니터링하십시오.
. 교체가 완료되면 다른 곳에서 사용하지 않는 이전 Secret을 삭제합니다.


.결과
메타데이터 암호화 키와 AppVault의 모든 Kopia 및 Restic 리포지토리는 새 암호로 보호되며, Trident Protect가 일시 중단한 일정이 다시 활성화됩니다.



[[monitor-password-rotation]]
== 비밀번호 변경 모니터링

비밀번호 변경 진행 상황을 확인하고 완료 여부를 확인할 수 있습니다.

.단계
. AppVault 보기:
+
[source, console]
----
kubectl -n trident-protect get appvault my-vault --output yaml
----
. 출력에서  `status.vaultPasswordRotation` 섹션을 확인하십시오. 회전이 진행되는 동안에는 다음과 같이 표시됩니다:
+
[source, yaml]
----
status:
  vaultPasswordRotation:
    state: Rotating
    rotated: 3
    pending: 1
    message: <message>
----
+
이 표는 필드를 설명합니다:

+
|===
| 필드에 입력합니다 | 설명 


| status.vaultPasswordRotation.state | 현재 회전 상태. 


| status.vaultPasswordRotation.rotated | 새 비밀번호를 사용하는 저장소 수입니다. 


| status.vaultPasswordRotation.pending | 백업 또는 복원 작업에서 사용 중이어서 건너뛴 저장소의 수입니다. 


| 상태.vaultPasswordRotation.메시지 | 최신 진행 상황 또는 실패 메시지. 
|===


.결과
회전은 다음 조건이 모두 충족될 때 완료됩니다:

* `status.vaultPasswordRotation`이(가) 존재하지 않습니다.
* `status.previousRepositoryPasswordSecretRef` 비어 있습니다.
* `status.repositoryPasswordSecretRef` 일치합니다 `spec.vaultPasswordSecretRef`.


.다음 단계
회전이 완료되지 않으면 다음 사항을 확인하십시오:

* *회전이 시작되지 않음*: `spec.enableRotation`이(가)  `false`일 수 있습니다. 이를  `true`(으)로 설정한 다음,  `spec.vaultPasswordSecretRef`을(를) 새 Secret으로 설정하십시오.
* *저장소가 대기 상태로 유지됨*: 백업 또는 복원 작업에서 해당 저장소를 사용 중입니다. 작업이 완료될 때까지 기다리십시오. Trident Protect는 대기 중인 저장소에 대해 자동으로 재시도합니다.
* *다른 AppVault가 잠금을 소유하고 있어 회전이 시작되지 않습니다*: <<버킷을 공유하는 AppVaults의 로테이션을 관리합니다>>을(를) 참조하십시오.
* *메시지 필드에 오류가 보고되었습니다*: 메시지에 설명된 문제를 해결하십시오. 로테이션은 중단된 지점부터 다시 시작됩니다.




[[migrate-from-datamoverpasswordsecretref]]
== dataMoverPasswordSecretRef에서 마이그레이션

기존 AppVault이 이전  `spec.dataMoverPasswordSecretRef` 필드를 사용하는 경우, 해당 필드를  `spec.vaultPasswordSecretRef`(으)로 이동할 수 있습니다.

.이 작업에 대해
Trident Protect는 하위 호환성을 위해  `spec.dataMoverPasswordSecretRef`를 유지합니다. 새로운 AppVaults에는  `spec.vaultPasswordSecretRef`를 사용하십시오.

.단계
.  `spec.dataMoverPasswordSecretRef` 및 해당 Secret을 그대로 유지하십시오.
.  `spec.vaultPasswordSecretRef`을(를) 사용하여 암호를 새 Secret으로 변경하십시오. <<볼트 비밀번호를 변경하십시오>>의 단계를 따르십시오.
. 순환 과정이 완료되면 AppVault에서  `spec.dataMoverPasswordSecretRef`을(를) 제거합니다.
. 다른 곳에서 사용하지 않는 경우 기존 Secret을 삭제하십시오.




[[manage-rotation-for-appvaults-that-share-a-bucket]]
== 버킷을 공유하는 AppVaults의 로테이션을 관리합니다

여러 AppVaults가 동일한 버킷과 접두사를 사용하는 경우, 그중 하나만 암호를 변경할 수 있습니다.

.이 작업에 대해
암호 순환에는  `password-rotation.lock`(이)라는 이름의 잠금 파일이 사용됩니다. 이 잠금에는 버킷 및 접두사에 대한 암호를 순환할 수 있는 AppVault의 UID가 기록됩니다. 두 번째 AppVault에  `spec.enableRotation: true`이(가) 있고 잠금에 다른 AppVault이(가) 지정되어 있으면 두 번째 AppVault은(는) 순환할 수 없습니다.

.단계
[role="tabbed-block"]
====
.다른 AppVault로 로테이션 전송
--
. 잠금을 소유한 AppVault에서 다음을 지웁니다 `spec.enableRotation`:
+
[source, console]
----
kubectl -n trident-protect patch appvault <current-owner> --type merge --patch '
spec:
  enableRotation: false
'
----
. 잠금이 해제될 때까지 기다리십시오.
. 다음에 로테이션해야 할 AppVault에서  `spec.enableRotation`을(를)  `true`(으)로 설정합니다:
+
[source, console]
----
kubectl -n trident-protect patch appvault <new-owner> --type merge --patch '
spec:
  enableRotation: true
'
----


--
.삭제된 AppVault가 남긴 잠금 제거
--
잠금을 소유한 AppVault가 더 이상 존재하지 않고 충돌 후와 같이 잠금이 제거되지 않은 경우 다음 단계를 따르십시오.

. 버킷의 AppVault 접두사에서  `password-rotation.lock` 파일을 삭제하십시오.
. 순환해야 하는 AppVault에서  `spec.enableRotation`을(를)  `true`(으)로 설정합니다:
+
[source, console]
----
kubectl -n trident-protect patch appvault <appvault-name> --type merge --patch '
spec:
  enableRotation: true
'
----
