= Trident Linux Unified Key Setup(LUKS)
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
Linux Unified Key Setup(LUKS)은 디스크 암호화 사양입니다. Trident는 LUKS를 사용하여 ONTAP SAN 및 ONTAP SAN ECONOMY 볼륨에 대해 볼륨별 호스트 측 암호화를 제공하며, 암호 순환 및 볼륨 확장을 지원합니다.

Trident에서 LUKS로 암호화된 볼륨은 에서 권장하는 AES-XTS-plar64 사이퍼 및 모드를 link:https://csrc.nist.gov/publications/detail/sp/800-38e/final["NIST"^]사용합니다.


NOTE: ASA r2 시스템에서는 LUKS 암호화가 지원되지 않습니다. ASA r2 시스템에 대한 자세한 내용은 다음을 참조하세요. link:https://docs.netapp.com/us-en/asa-r2/get-started/learn-about.html["ASA R2 스토리지 시스템에 대해 알아보십시오"^] .

.시작하기 전에
* 작업자 노드에는 Cryptsetup 2.1 이상(3.0 이하)이 설치되어 있어야 합니다. 자세한 내용은 를 참조하십시오 link:https://gitlab.com/cryptsetup/cryptsetup["Gitlab: cryptsetup"^].
* 성능상의 이유로 NetApp에서는 작업자 노드가 AES-NI(Advanced Encryption Standard New Instructions)를 지원하는 것이 좋습니다. AES-NI 지원을 확인하려면 다음 명령을 실행합니다.
+
[listing]
----
grep "aes" /proc/cpuinfo
----
+
아무 것도 반환되지 않으면 프로세서는 AES-NI를 지원하지 않습니다. AES-NI에 대한 자세한 내용은 다음 웹 사이트를 참조하십시오. link:https://www.intel.com/content/www/us/en/developer/articles/technical/advanced-encryption-standard-instructions-aes-ni.html["인텔: AES-NI(Advanced Encryption Standard Instructions)"^].





[[enable-luks-encryption]]
== LUKS 암호화를 사용합니다

ONTAP SAN 및 ONTAP SAN 이코노미 볼륨에 대해 Linux 통합 키 설정(LUKS)을 사용하여 볼륨별 호스트 측 암호화를 활성화할 수 있습니다.

.단계
. 백엔드 구성에서 LUKS 암호화 속성을 정의합니다. ONTAP SAN의 백엔드 구성 옵션에 대한 자세한 내용은 을 참조하십시오 link:../trident-use/ontap-san-examples.html["ONTAP SAN 구성 옵션"].
+
[source, json]
----
{
  "storage": [
    {
      "labels": {
        "luks": "true"
      },
      "zone": "us_east_1a",
      "defaults": {
        "luksEncryption": "true"
      }
    },
    {
      "labels": {
        "luks": "false"
      },
      "zone": "us_east_1a",
      "defaults": {
        "luksEncryption": "false"
      }
    }
  ]
}
----
. 사용 `parameters.selector` LUKS 암호화를 사용하여 스토리지 풀을 정의합니다. 예를 들면 다음과 같습니다.
+
[source, yaml]
----
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: luks
provisioner: csi.trident.netapp.io
parameters:
  selector: "luks=true"
  csi.storage.k8s.io/node-stage-secret-name: luks-${pvc.name}
  csi.storage.k8s.io/node-stage-secret-namespace: ${pvc.namespace}
----
. LUKS 암호를 포함하는 암호를 생성합니다. 예를 들면 다음과 같습니다.
+
[source, yaml]
----
kubectl -n trident create -f luks-pvc1.yaml
apiVersion: v1
kind: Secret
metadata:
  name: luks-pvc1
stringData:
  luks-passphrase-name: A
  luks-passphrase: secretA
----




[[use-luks-with-rwx-raw-block-volumes]]
== RWX 원시 블록 볼륨과 함께 LUKS 사용

Trident 26.10부터는  `ReadWriteMany`(RWX) 액세스 모드를 사용하여 여러 Kubernetes 노드에 연결된 iSCSI 기반 원시 블록 볼륨에 LUKS 암호화를 사용할 수 있습니다. 이는 라이브 마이그레이션 중에 소스 노드에 연결된 상태에서 대상 노드에 동일한 암호화된 볼륨을 연결해야 하는 KubeVirt 가상 머신 등 워크로드에 유용합니다.

RWX LUKS 지원은 원시 블록 볼륨으로 제한됩니다. 파일 시스템 모드 RWX LUKS 볼륨은 지원되지 않습니다. 애플리케이션은 복호화된 데이터에 대한 동시 접근을 조정할 책임이 있으며, Trident는 LUKS 작업만 조정합니다.

<<LUKS 암호화를 사용합니다>>에 설명된 대로 백엔드, StorageClass 및 암호 Secret에 LUKS를 구성합니다. 그런 다음 `volumeMode: Block` 및 `ReadWriteMany`을(를) 사용하여 PVC를 생성합니다:

[source, yaml]
----
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-rwx-pvc
  namespace: my-app
spec:
  accessModes:
    - ReadWriteMany
  volumeMode: Block
  storageClassName: san-luks-rwx
  resources:
    requests:
      storage: 10Gi
----
여러 노드의 Pod는 이 PVC를 원시 블록 장치로 연결할 수 있습니다. Trident는 처음 연결 시 LUKS2로 장치를 포맷하고 이후 노드에서 기존에 암호화된 볼륨을 엽니다. 암호 변경 및 볼륨 확장 등 기존 LUKS 작업이 지원됩니다.



[[why-trident-serializes-luks-operations]]
=== Trident가 LUKS 연산을 직렬화하는 이유

LUKS2는 암호화 헤더의 중복 복사본을 블록 장치 시작 부분에 저장합니다.  `cryptsetup`은(는) 복사본이 서로 다름을 감지할 때, 읽기 전용으로 보이는 명령을 실행하는 동안을 포함하여 헤더를 복구할 수 있습니다. 잠금은 노드에 국한되며 다른 노드의 작업을 조정할 수 없습니다. 한 노드가 헤더를 업데이트하는 동안 다른 노드가  `cryptsetup`을(를) 실행하면, 두 번째 노드가 헤더 복구를 트리거하여 업데이트를 중단시키고 헤더를 손상시킬 수 있습니다.

동시 헤더 접근을 방지하기 위해 Trident는 각 RWX LUKS 볼륨에 대해 Kubernetes 리스를 사용합니다. 노드가 볼륨에 대한  `cryptsetup` 명령을 실행하기 전에 리스를 확보해야 합니다. Trident는 작업이 성공적으로 완료되면 리스를 해제합니다. 리스가 확보된 동안 다른 노드가 작업을 요청하면 Trident는 재시도 가능한 오류를 반환하고 Kubernetes는 나중에 재시도합니다. 서로 다른 볼륨에 대한 작업은 독립적입니다.

 `cryptsetup` 작업이 실패하면 Trident는 의도적으로 리스를 유지하여 동일한 노드에서만 재시도할 수 있도록 합니다. 이유가  `LeaseRetained`인 경고 이벤트에 실패가 기록됩니다. 리스는 자동으로 만료되지 않습니다. 관리자는 해당 보유 노드에서  `cryptsetup` 작업이 실행되고 있지 않음을 확인한 후에만 리스를 제거해야 합니다. 복구 단계는 <<rwx-luks-stuck-lease,RWX Linux Unified Key Setup(LUKS) 볼륨에 대한 임대가 중단된 문제를 해결합니다>>을(를) 참조하십시오.

노드들이 순차적으로 볼륨을 열기 때문에, 여러 노드에서 워크로드를 시작하는 데 걸리는 시간이 암호화되지 않은 볼륨을 사용할 때보다 오래 걸릴 수 있습니다. Kubernetes는 현재 작업이 완료된 후 일시적인 잠금 오류를 재시도합니다. 대규모 스케일아웃 시 Pod는  `ContainerCreating`에 더 오래 머무를 수 있으며, 동일한 노드의 워크로드는 단일 열린 장치 매핑을 공유할 수 있습니다.



[[limitations]]
=== 제한 사항

LUKS - 암호화된 볼륨은 ONTAP 중복 제거 및 압축을 활용할 수 없습니다.



[[backend-configuration-for-importing-luks-volumes]]
== LUKS 볼륨을 가져오기 위한 백엔드 구성입니다

LUKS 볼륨을 가져오려면 백엔드에서 로(`true` 설정해야 `luksEncryption` 합니다. 이 `luksEncryption` 옵션은 볼륨이 LUKS 호환(`true`) 또는 LUKS 규격이 아닌 경우 Trident에 지시합니다.(`false`

[source, yaml]
----
version: 1
storageDriverName: ontap-san
managementLIF: 10.0.0.1
dataLIF: 10.0.0.2
svm: trident_svm
username: admin
password: password
defaults:
  luksEncryption: 'true'
  spaceAllocation: 'false'
  snapshotPolicy: default
  snapshotReserve: '10'
----


[[pvc-configuration-for-importing-luks-volumes]]
== LUKS 볼륨을 가져오기 위한 PVC 구성입니다

LUKS 볼륨을 동적으로 가져오려면 `trident.netapp.io/luksEncryption` `true` 이 예제에 표시된 대로 주석을 로 설정하고 PVC에 LUKS 사용 스토리지 클래스를 포함합니다.

[source, yaml]
----
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: luks-pvc
  namespace: trident
  annotations:
    trident.netapp.io/luksEncryption: "true"
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
  storageClassName: luks-sc
----


[[rotate-a-luks-passphrase]]
== LUKS 암호를 회전합니다

LUKS 암호를 회전하고 회전을 확인할 수 있습니다.


WARNING: 볼륨, 스냅샷 또는 비밀이 더 이상 참조하지 않음을 확인할 때까지 암호문을 잊지 마십시오. 참조된 암호가 손실된 경우 볼륨을 마운트할 수 없으며 데이터가 암호화된 상태로 유지되고 액세스할 수 없게 됩니다.

.이 작업에 대해
LUKS 암호 회전은 새 LUKS 암호를 지정한 후 볼륨을 마운트하는 POD가 생성될 때 발생합니다. 새 Pod가 생성되면 Trident는 볼륨의 LUKS 암호를 암호의 활성 암호와 비교합니다.

* 볼륨의 암호가 비밀의 활성 암호와 일치하지 않으면 회전이 발생합니다.
* 볼륨의 암호가 비밀의 활성 암호와 일치하면 가 됩니다 `previous-luks-passphrase` 매개 변수는 무시됩니다.


.단계
. 를 추가합니다 `node-publish-secret-name` 및 `node-publish-secret-namespace` StorageClass 매개 변수입니다. 예를 들면 다음과 같습니다.
+
[source, yaml]
----
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: csi-san
provisioner: csi.trident.netapp.io
parameters:
  trident.netapp.io/backendType: "ontap-san"
  csi.storage.k8s.io/node-stage-secret-name: luks
  csi.storage.k8s.io/node-stage-secret-namespace: ${pvc.namespace}
  csi.storage.k8s.io/node-publish-secret-name: luks
  csi.storage.k8s.io/node-publish-secret-namespace: ${pvc.namespace}
----
. 볼륨 또는 스냅숏에서 기존 암호를 식별합니다.
+
.볼륨
[listing]
----
tridentctl -d get volume luks-pvc1
GET http://127.0.0.1:8000/trident/v1/volume/<volumeID>

...luksPassphraseNames:["A"]
----
+
.스냅샷
[listing]
----
tridentctl -d get snapshot luks-pvc1
GET http://127.0.0.1:8000/trident/v1/volume/<volumeID>/<snapshotID>

...luksPassphraseNames:["A"]
----
. 볼륨에 대한 LUKS 암호를 업데이트하여 새 암호 및 이전 암호 문구를 지정합니다. 확인합니다  `previous-luke-passphrase-name` 및 `previous-luks-passphrase` 이전 패스프레이즈를 일치시킵니다.
+
[source, yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: luks-pvc1
stringData:
  luks-passphrase-name: B
  luks-passphrase: secretB
  previous-luks-passphrase-name: A
  previous-luks-passphrase: secretA
----
. 볼륨을 마운트하는 새 포드를 생성합니다. 이 작업은 회전을 시작하는 데 필요합니다.
. 패스프레이즈가 회전되었는지 확인합니다.
+
.볼륨
[listing]
----
tridentctl -d get volume luks-pvc1
GET http://127.0.0.1:8000/trident/v1/volume/<volumeID>

...luksPassphraseNames:["B"]
----
+
.스냅샷
[listing]
----
tridentctl -d get snapshot luks-pvc1
GET http://127.0.0.1:8000/trident/v1/volume/<volumeID>/<snapshotID>

...luksPassphraseNames:["B"]
----


.결과
볼륨과 스냅샷에 새 암호문만 반환되면 암호가 회전되었습니다.


NOTE: 예를 들어, 두 개의 암호 구문이 반환되는 경우 `luksPassphraseNames: ["B", "A"]`, 회전이 완료되지 않았습니다. 새 포드를 트리거하여 회전을 완료할 수 있습니다.



[[enable-volume-expansion]]
== 볼륨 확장을 설정합니다

LUKS 암호화 볼륨에서 볼륨 확장을 활성화할 수 있습니다.

.단계
. 를 활성화합니다 `CSINodeExpandSecret` 기능 게이트(베타 1.25+). 을 참조하십시오 link:https://kubernetes.io/blog/2022/09/21/kubernetes-1-25-use-secrets-while-expanding-csi-volumes-on-node-alpha/["Kubernetes 1.25: CSI 볼륨의 노드 기반 확장에 비밀을 사용합니다"^] 를 참조하십시오.
. 를 추가합니다 `node-expand-secret-name` 및 `node-expand-secret-namespace` StorageClass 매개 변수입니다. 예를 들면 다음과 같습니다.
+
[source, yaml]
----
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: luks
provisioner: csi.trident.netapp.io
parameters:
  selector: "luks=true"
  csi.storage.k8s.io/node-stage-secret-name: luks-${pvc.name}
  csi.storage.k8s.io/node-stage-secret-namespace: ${pvc.namespace}
  csi.storage.k8s.io/node-expand-secret-name: luks-${pvc.name}
  csi.storage.k8s.io/node-expand-secret-namespace: ${pvc.namespace}
allowVolumeExpansion: true
----


.결과
온라인 저장소 확장을 시작할 때 kubelet은 적절한 자격 증명을 드라이버에 전달합니다.
